# 第 7 轮：待办备忘录（替换左键效果）

日期：第 7 轮开发
主人需求：
> 增加备忘录功能，替换左键效果。左键点击后出现待完成任务的栏目，默认大小可装 5 栏、两列，
> 最上方为输入任务栏，输入的任务会列入下方栏目中，每栏左方有一个小方框，点击即表示完成任务并删除该栏。

## 实现（逐条对照需求）

| 需求 | 实现 |
|---|---|
| 左键点击触发 | `pet.click` → `toggleMemo()`（原"随机台词"已替换） |
| 默认装 5 栏 | `MEMO_CAP = 5`；未填满时渲染虚线空槽，主人一眼看到还能装几条 |
| 两列 | `.memo-grid { grid-template-columns: 1fr 1fr }` |
| 最上方输入栏 | `.memo-input`，**回车添加**，`Esc` 收起 |
| 任务列入下方栏目 | 按顺序填入网格，每条占一格 |
| 每栏左侧小方框 | `.memo-box` 按钮 |
| 点击方框＝完成并删除 | 先加删除线（220ms 反馈）→ 从数组移除 → 重排 → 空槽补回 |

额外做了：任务持久化（localStorage）、容量满提示、"还可以添加 N 条"提示、
点 `×` 收起面板、投喂计数（原"喂白饭"菜单项改为次数统计）。

## 三个必须解决的技术问题

### 1. 面板比窗口大 → 窗口要动态改尺寸

面板 288×183，窗口原来只有 200×250。展开时把窗口改成 312×430。

**两个连带的坑**：
- **改尺寸后必须重算穿透掩码**，否则点击判定范围还停留在旧尺寸上（角色变得很大，鼠标移到新区域却被当成空气穿透掉）
- **夹取到工作区时要用"实际尺寸"而不是设计尺寸**：Windows 会把窗口吸到物理像素网格，实际大 1~2px，
  用设计值算会导致右下角刚好越界（实测越界 1px 被自检抓出来）

### 2. 面板要能打字 → 需要键盘焦点

桌宠窗口平时不抢键盘焦点。`openMemo()` 里调 `win.focus() + webContents.focus()`，
再把焦点给输入框。

顺带发现一个**注册阶段问题**：
> `stopPropagation()` 只能阻止**后续阶段（冒泡）**，**挡不住捕获阶段**。

全局快捷键如果注册在捕获阶段，面板打开时输入框的 `stopPropagation()` 就形同虚设。
所以全局 `keydown` 必须注册在**冒泡阶段**，输入框才能真正"吞掉"按键。

### 3. 面板展开会盖住桌宠 → 测试必须隔离

自检里"点击"这条测试在阶段 4 变成了"展开面板"。面板一旦展开就一直盖着角色，
导致**后面所有交互断言全部点到面板上**（点击、拖动、右键、气泡全挂）。

修法：面板测试独立成块，每块结束时**收起面板 + 清空任务 + 等 800~900ms**
（等窗口缩回、掩码重算完成），再做后续断言。

## 本轮踩的坑（都是人家自己的错）

| # | 现象 | 根因 |
|---|---|---|
| 1 | `js is not defined` | 自检主流程里本没有 `js` 辅助函数，人家直接在那边用了 |
| 2 | 容量断言"6 次添加成功 6 次" | **字段名冲突**：`memoAdd` 返回 `{added: 布尔, ...memoSnapshot()}`，而 snapshot 里也有 `added`（累计计数器），把布尔值覆盖了 |
| 3 | 断言"成功次数为 0" | 修了冲突但数据仍不对——因为上一条的取值方式错了，改 `=== true` 严格判定 |
| 4 | `removed` 显示 `undefined` | 同样是字段名冲突，快照字段改名 `addedTotal` / `removedTotal` |
| 5 | 自检超时 | 面板测试新增了多次窗口缩放 + 掩码重算，15 秒兜底不够 → 放宽到 60 秒 |
| 6 | `trace()` 崩在 `null.getBounds()` | 自检跑得太久、窗口已关闭；`trace()` 加空值保护 |
| 7 | "键盘被输入框接管"断言失败 | 测试辅助函数把事件直接 dispatch 到 `window`，**根本没经过输入框**；改成从输入框派发走真实冒泡路径 |
| 8 | 同上，仍然失败 | `from` 读的是**上一次测试的陈旧值**；改成用"触发前后计数增量"判定 |

> **教训**：这一轮 8 个坑里有 4 个是**测试自己的问题**（字段冲突、陈旧值、派发目标错误）。
> 人家再次确认那条老经验：**断言写错的数据，比不写断言更误导人**——它会让人去改本来正确的功能代码。

## 已知限制

1. **只有 5 栏**，满了必须先勾掉一条（按主人要求；要改成可滚动/可扩展告诉人家）
2. 任务**不分优先级、无截止时间**（就是个轻量便签）
3. 面板展开时占屏幕 312×430，位置跟随桌宠（贴屏幕顶部时会被夹取到工作区内）
4. `localStorage` 存在 Electron 的 userData 目录，**换个 userData 就跑不到旧数据**（自检环境即如此）

## 补章：超过 5 条改为可滚动

主人反馈：**「默认大小可装 5 栏」里的"默认"应该指可见高度，不是硬上限。**

### 改动

| 之前 | 现在 |
|---|---|
| 第 6 条起被拒绝，提示"已满 5 条" | **不限条数**，第 6 条起列表区域自动可滚动 |
| `MEMO_CAP = 5` 硬上限 | `MEMO_VISIBLE = 5` 默认可见栏数 |
| 满时提示先勾掉一条 | 可滚动时提示「共 N 条 · 向上滚动查看更多」 |

面板与窗口尺寸**保持不变**（滚动只发生在列表区域内部）——这样任务增减时窗口不会跳动、
也不用反复重算穿透掩码。

顺带做了：**添加新任务时自动滚动到底**，保证刚输入的那条一定看得见；
滚动时底部有渐隐提示，让主人知道下面还有内容。

### 踩的坑：滚动高度给错了层级

一开始把 `max-height: 130px; overflow-y: auto` 直接加在 `.memo-grid` 上，结果**不滚动**。

量了 DOM 才明白：

```
.memo-grid { grid-auto-rows: 22px; max-height: 130px }   ← 行被压到 15px 去塞进 130px
grid.clientHeight = 103，scrollHeight = 103，maxScroll = 0
```

`grid-auto-rows` 会把行高**压缩**去适配 `max-height`，所以是"行变矮"而不是"内容溢出"。

修法：高度给在**外层容器** `.memo-scroll { height: 130px; overflow-y: auto }`，
网格在容器里自然撑开（184px），于是正常溢出滚动。

### 还踩了两个测试自身的错

1. **测试塞的任务不够**：两列布局下 8 条只排 4 行（103px），130px 容器装得下，当然不滚动。
   真正触发滚动需要 **11 条以上**（超过 5 行）。→ 测试改为塞到 14 条。
2. **量错了元素**：断言读 `#memoList`（内层网格，本来就不滚）的 `scrollTop`，得到 0，
   却因为几何判断侥幸通过了。改成量 `#memoScroll`（外层容器）后数据自洽：
   `scrollTop=54 / maxScroll=54`。
3. **同步删除通道**：真实删除带 220ms 删除线动画，测试循环连续调用会互相打架
   （任务在中途就被删空）。加了 `memoCompleteNow()` 同步入口专供自检。

## 补章 2：修正面板出现的位置与方式（主人澄清）

主人的反馈分两次，第二次才是准确的：

> **「人物先让位到下方 → 再在原位置展开面板」这是目前情况，期望是直接在右边生成。**

也就是说：**点击后桌宠本身不该动，面板应该在她旁边直接出现。**

### 之前错在哪（量出来的，不是猜的）

用探针量了一次，问题一目了然：

```
收起: 窗口 202x254@754,409   桌宠屏幕位置 [810,497]
展开: 窗口 320x255@754,409   桌宠屏幕位置 [997,498]   ← 她跑了 187px
      面板宽 280（被压缩了），窗口 320 装不下 288+130 → panelLeft = -69（被裁掉）
```

三个叠加的根因：

| # | 问题 | 根因 |
|---|---|---|
| 1 | 面板被裁掉 | `setPanel` 确实收到了 `{open:true}`，但窗口**没按预期变宽**；而且 320px 也不够装 288 面板 + 130 桌宠 |
| 2 | 桌宠"往下/往右跑" | `.scene` 的 `align-items` 被 `panel-right` 类从 `flex-end` 改成了 `flex-start`，窗口一变宽她就被重排 |
| 3 | 面板宽度只有 279 | flex 把 288 的项**压缩**了 |

### 改法：换成 CSS Grid 固定列宽

flex 的"拉伸/收缩"是漂移的根源，所以直接放弃它，用 grid 把列宽钉死：

```css
/* 收起态：单列，桌宠贴右边缘 */
.scene { display: grid; grid-template-columns: 158px; justify-content: end; align-items: end; }

/* 展开态：两列 [面板 300px][桌宠 158px] —— 桌宠仍在最右列，所以屏幕位置恒定 */
.scene.memo-open { grid-template-columns: 300px 158px; grid-template-areas: "memo pet"; }
```

主进程侧：窗口宽度 `200 → 470`（面板 288 + 桌宠列 158 + 余量），
并且**优先把面板放在桌宠左边**（因为桌宠默认贴屏幕右下角，右边通常没空间），
窗口向左扩展 → 桌宠的屏幕坐标天然不变。

### 顺带修掉的尺寸漂移

收起面板时用了 `height: b.height`（当前高度）而不是设计高度，
于是**每开合一次窗口就长高几像素**：

```
交互开始=200x258 → 收起后=200x264 → 再收起=200x270   ← 累积漂移
```

改成收起时**明确还原到设计尺寸 200×250** 后稳定了：

```
200x251 → 470x251（展开）→ 200x251（收起）→ 470x251 → 200x251
```

### 新已知限制

1. 面板**优先放左侧**（桌宠通常在最右下角，右侧没空间）；只有在左边也放不下时才会放到右侧，
   那种情况下窗口改为向右扩展、桌宠保持在原位（实测仍为 0 偏移）
2. 面板与桌宠同高（250px），所以面板高度不会超过桌宠窗口高度
3. 面板宽度固定 288px，不随任务长度自适应
