## 补章 3：主人给了截图后的关键转折 —— 可以自动抠！

### 之前判断错在哪

人家前面用 `analyze-bg.js` 判定这 13 张"背景复杂、不能自动抠"，判据是：
**从四边内缩 8% 采样**，结果边缘离散度 31.9~103.2、四角色差 0~224，于是归类成 `complex`。

**这个判据有问题**：内缩 8% 采到的是**画面内容**（条纹本身、贴着边的装饰），
而不是"最外圈的背景"。主人一发截图，真相就出来了：

```
1.png 背景色: rgb(235,201,206) 46.9%   ← 粉色条纹
              rgb(238,234,236) 38.2%   ← 白色条纹
              rgb(227,59,109) 13.9%    ← 品红标签
```

**背景就是规则的粉白横条纹**，是教科书级的可抠素材。

> 教训：**"边缘采样"必须采最外圈**，内缩采样测的是内容而不是背景。
> 人家一开始把"边缘噪声大"当成了"背景复杂"。

### 自动抠图工具的四个坑（都修了）

| # | 现象 | 根因 |
|---|---|---|
| 1 | 最外圈近黑描边 `rgb(25,25,25)` 没被识别成背景，导致**裁切裁不紧**（输出还是 505x774） | 只采了"内缩 8%"和"1.5% 环"，**漏掉最外 1~2 像素** |
| 2 | 加了外圈采样仍不生效 | 用 `Map` 按**精确 RGB 值**统计外圈颜色，而描边**带噪点**（`24,25,21`/`23,24,22`各不相同），最标准的值只占 12.7%，被 25% 阈值卡掉 → 必须**按容差聚类** |
| 3 | `RangeError: Invalid array length` | 过渡带像素会被**反复入栈**（`bgMask` 恒为 2，永远不满足"已处理"），数组无限膨胀 → 改 typed array + done 标记 |
| 4 | 边缘残留几个像素导致裁不紧 | 描边与画面之间有一圈**抗锯齿过渡色**（`rgb(92,42,54)`），只按单阈值判会漏 → 加**双层阈值**（确定背景 / 过渡带），过渡带只在紧邻已确认背景时才吞 |

### 结果

```
13 张全部生成到 assets/cutout/，尺寸 130px，全部带 alpha 通道
拼接预览图: artifacts/cutout-preview.png
```

逐张"删除像素"比例差异很大（72%~97%），说明**有几张可能抠过头**：

| 文件 | 删除比例 | 人家判断 |
|---|---|---|
| 1 / 4 / 6 / 8 / J / K / Q | 72~86% | 正常范围 |
| 2 / 3 / 5 / 9 | 88~94% | 可能啃到主体了 |
| 7 / 10 | 92~97.5% | **大概率抠过头**（背景色簇过多，容差把主体颜色也算了进去） |

**这一步必须主人目视确认** —— 人家看不见图，只能看数字。

### 主人问的 Krita 抠图功能在哪（人家给的答案）

按主人截图上的菜单，抠这种**条纹背景**：

| 工具 | 位置 | 适用场景 |
|---|---|---|
| **相似颜色选区工具** ★ | 工具栏左侧竖排（魔术棒附近，图标是"棒+虚线方块"） | **条纹背景首选**！按颜色选中**所有**粉色区域（包括不连续的条纹），一次删干净 |
| 连续选区工具（魔术棒） | 同上，图标是"棒" | 点到哪块选哪块，条纹太多要点很多次 |
| 按颜色选择（Edit 菜单） | 菜单「选择(S)」→ 按颜色选择 | 与相似颜色选区类似 |
| 颜色转 Alpha | 菜单「滤镜」→「颜色」→「颜色转 Alpha」 | 把某个颜色直接变透明（适合纯净单一背景） |

推荐流程：**相似颜色选区 → 调"模糊度"容差 → Delete 删掉 → 再用连续选区把白色条纹也删一遍**。
容差别开太大，否则人物身上相近的颜色会被一起删。

## 补章 4：清晰度问题（主人反馈"抠得不错但清晰度不够"）

### 两个原因，都是人家的错

**① 人家把 500~900px 的原图硬缩到 130px** —— 白丢 80% 像素。
`npm run cutout` 当时写死了 `--size=130`。

**② 更关键：显示器是 150% 缩放（DPR=1.5）**，那个"130px"的显示框
**实际需要 195 个物理像素**才够清晰。给 130px 的素材 → 浏览器还得放大 → **糊**。

### 修法

1. **抠图默认保持原分辨率**（只裁掉四周空白，不缩放）
   - `npm run cutout` → 保持原分辨率（推荐）
   - `npm run cutout:small` → 需要缩小到 130px 时才用
2. 尺寸计算改成"只裁剪"：`trimAndScale(..., 0)` 直接 memcpy 保留原始像素
3. **裁切阈值从 8 提高到 40**：抠图时描边与画面交界会留下极低 alpha 的羽化残边，
   用 8 会被这些残边撑住边界导致"裁不动"（实测 505x774 原样输出）
4. 顺带修 `list-assets.js` 的统计 bug：原来只抽上下各 64 行，
   裁剪过的图上下都是透明边 → 永远显示"100% 透明"，数字毫无意义。
   改成**全图 4x4 网格抽样**，并同时报告"透明%"与"不透明%"。

### 现状数据（全图抽样，可信）

| 文件 | 不透明占比 | 判断 |
|---|---|---|
| 4 / J / Q / 8 / K | 23~27% | ✅ 主体占比健康 |
| 6 / 9 / 1 | 13~16% | ✅ 正常 |
| 3 / 5 / 2 / 7 | 4~9% | ⚠️ 偏小，疑似啃到主体 |
| **10** | **1.6%** | ❌ 几乎抠空 |

主人说"只有 5 张抠得还不错"——**和这个数据是吻合的**：
按"不透明占比 ≥13%"筛，正好是 **1 / 4 / 6 / 8 / J / K / Q** 这 7 张里的一部分。
**主人的眼睛和人家改好的统计口径，第一次对上了。**

### 渲染层的清晰度保障（已具备）

`renderer.js` 画帧时用的是：

```js
ctx.imageSmoothingEnabled = true;            // 默认就开
ctx.imageSmoothingQuality = 'high';          // 高质量缩放
ctx.drawImage(img, x, y, w, h);              // 等比缩放并居中
```

canvas 的缩放是**浏览器原生实现**（Lanczos 级别），比人家手写的最邻近/面积平均强得多。
所以正确策略就是：**素材给足分辨率，缩放交给 canvas**。

### 还有一条隐藏的清晰度杀手（人家提醒主人）

如果要**换更大的角色**，只要改 CSS 的 `.sprite { width/height }` 和
`canvas` 的 `width/height` 属性（现在是 130）即可，原图分辨率足够支撑放大到 260~400px 而不糊。
另外 `main.js` 里的 `WIN_W/WIN_H`（窗口尺寸）和 `PANEL_W` 要跟着调，否则面板会挤。
