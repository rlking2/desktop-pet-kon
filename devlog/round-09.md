### 踩到的一个坑（值得记）

第一次跑 `npm run autotest` **退出码 0 但 `artifacts/selfcheck.json` 没更新**——
因为主人桌面上正跑着一个桌宠实例（16:13 启动），`app.requestSingleInstanceLock()` 让它拿了锁，
人家的自检实例启动即 `app.quit()`（退出码也是 0，**看起来像"全部通过"**）。

> 教训：**退出码 0 不等于自检跑过了**，必须核对 `artifacts/selfcheck.json` 的时间戳。
> 绕开办法：给自检实例单独指定 `--user-data-dir`，锁就分开了，不用去动主人正在用的那个实例。
> 这条命令已记在下面。

```powershell
$env:DSH_PET_AUTOTEST='1'
& "node_modules\electron\dist\electron.exe" . --user-data-dir="$PWD\artifacts\tmp-userdata"
```

## 补章：主人给的「开心」素材（把动作换成这张图）

主人甩了一张图：**「把开心的动作替换为这张」**。

### 先说一个关键发现：这张图**已经在仓库里了**

人家把附件算了 SHA256：

```
附件 frame-03.png       C3AEE7B200A588B9983680E871E12D0CCD3E401C6797A6B388AE55F2D96DE145
assets/idle/frame-03.png C3AEE7B200A588B9983680E871E12D0CCD3E401C6797A6B388AE55F2D96DE145  ← 一模一样
```

也就是说，主人是从 `assets\idle\` 里挑了一张图给人家（文件名也叫 `frame-03.png`）。
**这不是"新素材"，是"把待机里的第 3 帧也当成开心动作"**。
所以人家的做法不是重新抠图，而是**建一个 `happy` 素材组、把这张图放进去、走同一条流水线**。

### 素材流水线（人家这次才真正读懂它）

| 步骤 | 命令 | 说明 |
|---|---|---|
| 1 | 把图放进 `assets\happy\frame-01.png` | 目录名 = 动作组名 |
| 2 | `node scripts\inspect-assets.js --write --normalize-height happy` | 对齐 + 缩放 + 写 manifest |
| 3 | 产物 `assets\build\frames\happy\frame-000.png` + `assets\manifest.json` | 运行时读这两样 |

**`--normalize-height` 的真相（人家一开始理解错了）**：
它把一组里的主体缩放到"**该组**最高帧的 85%"。于是每组的表现都是
"画布 ≈ 组内最大包围盒 + 4、主体 = 该画布的 85%"，屏上角色高度就都落在
`0.85 × 200 ≈ 170px` 附近——**这正是"各动作组角色大小一致"的实现方式**。

人家当时还担心"happy 是单帧，画布只有 687x1090，角色会比 idle 的 901x1203 显得大 10%"，
于是动手量了每个成品帧里**最大连通块**（真正的角色主体，不含彩纸装饰）：

```
组/帧              画布        主体(连通块)   屏上高度
idle/frame-000     901x1203    435x715       118.9px
idle/frame-001     901x1203    385x814       135.3px
idle/frame-002     901x1203    352x765       127.2px
happy/frame-000    687x1090    319x694       127.3px   ← 和 idle/frame-002 是同一张图，差 0.1px
interact/frame-000 484x659     218x466       141.4px
hover/frame-000    687x987     394x713       144.5px
```

**结论：不用担心**——happy 和"同一张图在 idle 里"渲染出来一样大（127.3 vs 127.2）。
（顺带量出 idle 三帧本身有 119~135px 的波动，那是原图取景差异，属于既有现象，
不是本次改动引入的。）

### 单帧素材 = 一闪而过 → 加了 `holdMs`（末帧定格）

`interact` 是 3 帧 × 204ms = 612ms，看得见；
而 happy 只有 **1 帧**，播完就收尾 = **204ms**，比眨眼睛还短。

于是在时间线里加了 `holdMs`（"末帧定格"）：

```js
// tick() 里：最后一帧的延时不用素材的 delayMs，改用 holdMs
const isLastFrame = spriteState.activeFrame >= g.images.length - 1;
const frameDelay = (isLastFrame && spriteTimeline.holdMs) ? spriteTimeline.holdMs : (g.delays[...] || 204);
```

「开心」分支里：`holdMs: still ? HAPPY_HOLD_MS : 0`（`HAPPY_HOLD_MS = 1000`），
即 **单帧素材定格 1 秒**；再叠一个 CSS 蹦跳（否则画面完全静止，看不出"开心"）。
多帧素材时定格自动关掉——主人以后想画成逐帧动画，直接多丢几帧进 `assets\happy\` 就行。

### 又踩了一个坑：**`npm run assets:write` 会把 13 张挑图当成动作组**

人家第一次直接跑 `npm run assets:write`（为了复现旧产物），结果：

```
提示：assets\ 下有 13 个孤立 PNG…
===== 素材「Q」（单张图）=====   FAIL 1 帧的 PNG 没有 alpha 通道
已输出: assets\manifest.json + 1 张对齐帧 → assets\build\frames\Q
```

`assets\1.png … Q.png` 全被当成"单张图动作组"写进了 manifest（多出 13 个组 + 13 个 build 目录），
而**旧 manifest 里只有 idle/interact/hover**——说明当初是**按组加 filter 跑的**。

修法：把 manifest 收敛回 4 个组、删掉多出来的 build 目录，并**把这条写进 `assets\README.md`**，
免得下次再踩。另外还要提一句：这次实验也**确认了旧产物的生成参数**
（用 filter + `--normalize-height` 重跑，idle/interact/hover 的 SHA256 与旧产物**逐字节相同**），
所以人家可以放心重跑流水线。
